# AWS KMS architecture decision records

Architect's pack: AWS KMS, from the Key Management Lifecycle app (kms.govassured.com). Facts checked against AWS and NCSC pages on 4 November 2026; check current documentation before relying on them. Codes in square brackets refer to the Sources list at the end.

## ADR template

| Field | What to record |
|---|---|
| Title | ADR-NNN: short noun phrase naming the decision |
| Status | Proposed \| Accepted \| Superseded by ADR-NNN \| Deprecated |
| Date and review date | When decided; when it must be reviewed (for example, at the next annual key review) |
| Decision owner | A role, not a person: service owner, security architect, SIRO delegate |
| Context | Workload, data classification, threats, regulatory and residency constraints, and options considered |
| Decision | What we will do, in one or two sentences |
| Consequences | Security, operational, cost and lock-in effects, both positive and negative |
| Controls and guardrails | Policies, SCPs/RCPs, Config rules and alarms that enforce the decision |
| Evidence | What an assessor can inspect: Config results, CloudTrail queries, policy files in source control |
| Mappings | NCSC Cloud Security Principles and CAF contributing outcomes |
| Sources | Official documentation used, with the date checked |

## ADR-001: Use customer managed KMS keys, not AWS managed keys, for workload data

- **Status:** Proposed (adapt and accept locally)
- **Decision owner:** service owner, with the security architect

### Context

AWS managed keys are a legacy key type: services launched since 2021 use AWS owned keys instead. You cannot change their key policies, rotate them on demand, or schedule their deletion, and RCPs do not apply to them. Customer managed keys give full lifecycle and policy control, at a monthly cost per key. [S29, S124, S129, S103]

### Decision

Every workload data store holding OFFICIAL data or above uses a customer managed key whose key policy separates administrators from users. AWS owned or AWS managed keys are accepted only where a service offers no customer managed key option, and that exception is recorded.

### Consequences

- Each key costs $1 per month (prorated hourly), plus rotation charges; request charges are unchanged.
- Teams must own key policies; misconfiguration can lock out access, so the policy lockout safety check stays on.
- RCPs, SCP guardrails and Config rules can now be applied to these keys. [S103, S97, S129]

### Controls and guardrails

Policies P1 and P11; Config rule kms-key-policy-no-public-access; required tags (kms-key-tagged).

### Evidence

Inventory of keys with KeyManager = CUSTOMER per data store; Config compliance export.

### Mappings

P2.3 data encryption; P14.1 secure by design; CAF B3.c stored data. [S4, S12, S24, S151]

## ADR-002: Key granularity: one key per application, environment and data classification

- **Status:** Proposed (adapt and accept locally)
- **Decision owner:** service owner, with the security architect

### Context

NCSC advises using a different root key encryption key for each application. In AWS KMS, access is controlled per key by its key policy, and the blast radius of a disabled or compromised key is everything encrypted under it. Quotas are generous (100,000 KMS keys per account and Region) but each key has a monthly cost. [S2, S37, S102, S103]

### Decision

Create one customer managed key per application × environment × data classification, in the account that owns the data or in the central key account. Never share keys between production and non-production. Use separate keys for logs and for backups.

### Consequences

- Smaller blast radius and simpler least-privilege key policies.
- More keys to tag, monitor and pay for; automation (infrastructure as code) is required.
- Aliases follow the naming standard so applications never hard-code key IDs. [S2, S104]

### Controls and guardrails

Naming and tagging standard; Config rule kms-key-tagged with required tag keys.

### Evidence

Key inventory with app, env and data-class tags; no key used by principals from two environments (CloudTrail query).

### Mappings

P14.2 help customers meet responsibilities; CAF A3.a asset management; CAF B3.c. [S14, S24, S151]

## ADR-003: Use AWS-generated key material; import key material only where a regulation requires it

- **Status:** Proposed (adapt and accept locally)
- **Decision owner:** service owner, with the security architect

### Context

With imported material you are responsible for its generation, a durable copy, and its expiry. If it expires or is deleted the key becomes unusable at once, and if you lose your copy the data is unrecoverable. AWS suggests imported keys in the standard key store when you must demonstrate control over key material. [S110, S111, S116, S31]

### Decision

Default to key material generated by AWS KMS. Import material only when a named regulation or contract requires customer-generated keys, and then: keep an escrowed copy under dual control, set an expiry only if required, and alarm on SecondsUntilKeyMaterialExpires.

### Consequences

- Avoids an outage mode that AWS-generated keys do not have.
- Where imported, the runbook R6 and the expiry alarm are mandatory.
- Automatic rotation is only for AWS-generated material; imported keys rotate on demand after new material is imported. [S112, S41]

### Controls and guardrails

Alarm A2; runbook R6; Config rule kms-cmk-not-scheduled-for-deletion.

### Evidence

List of EXTERNAL-origin keys with justification; alarm configuration; escrow procedure.

### Mappings

P2.3 data encryption; CAF B5.c backups; CAF D1.a response plan. [S4, S21, S155]

## ADR-004: Single-Region keys in Europe (London) by default; multi-Region keys by exception

- **Status:** Proposed (adapt and accept locally)
- **Decision owner:** service owner, with the security architect

### Context

AWS KMS is Regionally isolated. Multi-Region keys share key material and key ID across Regions, so ciphertext can be decrypted in several geographic locations. AWS lists one UK Region, so any replica is outside the UK. AWS advises using a multi-Region key only when you need one. [S123, S47, S113, S49]

### Decision

Create single-Region keys in eu-west-2. For cross-Region DR, re-encrypt copies under a single-Region key in the target Region. Use multi-Region keys only with an accepted data-location decision, a named DR role and SCP guardrails.

### Consequences

- UK data location is preserved by default.
- Cross-Region DR copies must be re-encrypted under a key in the target Region.
- If multi-Region keys are approved, each replica needs its own key policy review. [S114]

### Controls and guardrails

SCP P7 statement DenyMultiRegionKeys; key policy condition kms:ReplicaRegion where replicas are allowed.

### Evidence

No keys with MultiRegion = true outside the approved list; SCP attached to the root or OUs.

### Mappings

P2.1 physical location and legal jurisdiction; P2.5 resilience; CAF B5.b design for resilience. [S4, S155]

## ADR-005: Use the AWS KMS standard key store; custom key stores only when explicitly mandated

- **Status:** Proposed (adapt and accept locally)
- **Decision owner:** service owner, with the security architect

### Context

Standard KMS keys are generated in and protected by FIPS 140-3 Level 3 validated HSMs. AWS advises a custom key store only when regulation explicitly mandates a single-tenant HSM or an HSM you control outside AWS. Custom key stores lose asymmetric and HMAC keys, imported material, automatic rotation and multi-Region keys, and add cost and operational risk. [S31, S32, S33]

### Decision

Use the standard key store. A CloudHSM key store is allowed only for a documented single-tenant HSM requirement; an external key store only where keys must stay outside AWS. Both need an availability design and a disconnect runbook.

### Consequences

- Highest availability and lowest operating cost by default.
- CloudHSM key stores need at least two active HSMs in different Availability Zones, charged per HSM hour.
- External key stores make your key manager part of every AWS request path. [S122, S103, S120]

### Controls and guardrails

Approval gate before CreateCustomKeyStore (IAM restricted to the platform role); alarm on key store disconnection.

### Evidence

describe-custom-key-stores output; HSM count and AZ spread; DR test record.

### Mappings

P2.3 data encryption; P5 operational security (provider); CAF A2.a risk management process. [S4, S148, S153]
